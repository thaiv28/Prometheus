# Deployment

Prometheus is served at **https://prometheus.thaiv.dev** from AWS, through the `thaiv.dev` platform defined in `~/repos/project-platform-infrastructure` (AWS CDK).

## Infrastructure (owned by project-platform-infrastructure)

- Stack `ThaivPrometheusProject` (`us-west-2`): a private, versioned S3 bucket behind CloudFront with origin path `/current`, the shared `*.thaiv.dev` wildcard certificate, Route 53 A/AAAA aliases, `/404.html` served for missing paths (status 404), and lifecycle rules (since 2026-10-07, infra PR #14): `releases/` expires after 14 days, noncurrent versions after 30, incomplete multipart uploads after 1.
- Deploy access: the shared GitHub OIDC role from `ThaivProjectPlatform` (any `thaiv28/*` repo on `main`), granted this bucket and distribution through the managed policy `thaiv-prometheus-static-deployment`.
- Infrastructure changes are made in that repo and deployed with its **Deploy Prometheus Infrastructure** workflow (`diff`, then `deploy`). That workflow only touches this stack.

## Publishing (this repo)

`.github/workflows/publish.yml` runs on push to `main`, daily at 10:00 UTC, on manual dispatch, and as a build-only check on pull requests (PRs also run `benchmarks.yml`, below):

1. `check` (every run, alongside `build`; deploy waits for both): `uv sync` (with the dev group; it installs the package and its `prometheus` command too), `ruff format --check`, `ruff check`, and `pytest` (the e2e tests build a small DB from the committed CSV sample, so no download is needed).
2. `changes`: on a PR that touches only `docs/` and root Markdown files, `build` is skipped (shown as skipped, which satisfies a required check). Every other run builds.
3. `build`: `uv sync`, restore the CSV cache, `scripts/setup_db.sh --download-only` (downloads Oracle's Elixir's CSVs only on `main` and only once per data day, see *Data backup*), then the DB: restored from the Actions cache entry `prometheus-db-<hash>`, where the hash covers `data/raw/*.csv`, `scripts/setup_db.sh`, `scripts/0*`, `prometheus/**` except `prometheus/site/**`, and `uv.lock`; on a miss `setup_db.sh` rebuilds it (about 1.5 minutes) and a `main` build saves it under that key (PRs only restore), restore the prediction log from the backup bucket (main only, `scripts/prediction_log.sh restore`, see *Prediction log*), then one step running `scripts/build_site.py` (which fetches the match schedule from Leaguepedia and updates the log) alongside two read-only checks on the full DB: the e2e tests again (`PROMETHEUS_E2E_DB=real pytest -m e2e`) and `scripts/evaluate_metrics.py --check-weights` (refits the Form and FORGE weights, prints every change, and adds a warning annotation, not a failure, if a FORGE blend weight moved more than 10%); the step fails if any of the three does, and prints the checks' logs in groups. Then save the log back (`prediction_log.sh save`) and, except on PRs, upload `output/` as an artifact for `deploy`.
4. `deploy` (on `main` only, and only once the repo variables exist): assume `AWS_ROLE_ARN`, run `scripts/deploy_site.py` on the build's artifact, invalidate CloudFront (`/*`), and health-check the site.

### Uploads (`scripts/deploy_site.py`, since 2026-10-07)

The deploy writes straight into `s3://$DEPLOYMENT_BUCKET/current/` and sends only files whose content changed. `s3://$DEPLOYMENT_BUCKET/deploy/manifest.json` (outside `current/`, so not served) holds the SHA-256 of every file of the last deploy. Each run hashes `output/`, uploads the changed and new files, deletes the removed ones, re-uploads `kalshi.json` and `predictions.json` with `Cache-Control: max-age=300` every time (see *Hourly Kalshi prices*), and writes the new manifest. The manifest is deleted before any file changes and written only after the upload succeeds, so a failed run leaves none and the next run uploads every file (`aws s3 cp --recursive`, then `aws s3 sync --delete` to remove leftovers). Dispatch the workflow with **full_upload** checked to force that. `aws s3 sync` alone can't skip unchanged files: it compares size and timestamp, and every artifact download is new.

Pages carry no build date (the footer's "Last updated" was removed; only the home page's title line has it), so a page changes only when its content does. Before this, each deploy uploaded all ~11,200 files to `releases/<run id>` and then copied them into `current/` (~22k requests, ~6 of a push run's ~10 minutes).

The game-log JSON (~110 MB) is uploaded uncompressed: CloudFront's `CachingOptimized` policy already compresses JSON at the edge, and with changed-only uploads most of it isn't re-sent.

Runs share a concurrency group per ref (`deploy-prometheus-<ref>`; a PR's ref is `refs/pull/<n>/merge`). A new push to a PR cancels that PR's run in progress; runs on `main` (push, schedule, dispatch) are never cancelled and queue instead. PR runs never wait on or cancel a main publish.

This mirrors the shared `thaiv28/project-platform-workflows` `deploy-static.yml`, which can't be reused directly because it builds with npm.

CSS and JS links carry a content-hash query (`?v=`, from `asset()` in `prometheus/site/render.py`), so a deploy that changes them reaches browsers that cached the old files; the CloudFront invalidation only clears the edge. Since 2026-10-08 the deploy uploads CSS and JS with `Cache-Control: public, max-age=31536000, immutable` and fonts with `public, max-age=2592000` (`deploy_site.cache_control`), so repeat visits don't re-ask for them; pages and JSON carry none and get CloudFront's default. The edge cache key ignores the query string, which is why the `/*` invalidation on every deploy stays. A file uploaded before then gets its header when it next changes, or on a **full_upload** dispatch.

## Benchmarks on pull requests (`.github/workflows/benchmarks.yml`)

- Runs on `pull_request` only (opened, synchronize, reopened, labeled, unlabeled); never on `main` pushes, schedules or dispatch. Concurrency group `benchmarks-<PR number>`, cancelling the PR's older run. Permissions: `contents: read`, `pull-requests: write` (the comment).
- Three jobs. `prepare` reads any stored verdict to reuse (label changes), the base commit (the merge commit's first parent) and whether its scripts have `--dump`, and looks up the newest `oracles-elixir-*` cache entry. `bench` runs as a matrix, `head` (the merge commit) and `base` × `core` and `markets`, in parallel, each on its own runner: `uv sync`, that exact CSV entry (so both read the same data; no `REFRESH_DATA`, so Drive only if the cache is empty), the cached DB under the same `prometheus-db-<hash>` key as `publish.yml` (usually a hit for the base, and for the head when the PR leaves the DB build alone), else `setup_db.sh`, then (`core`) the three benchmark scripts at once (`--dump`; they only read the DB) or (`markets`) `evaluate_markets.py --offline --dump` on the Kalshi cache entry `prepare` picked, uploading `dumps/` as an artifact. `markets` runs only when a `kalshi-markets-*` cache exists and the base's `evaluate_markets.py` has `--dump`. The base's dumps are cached as `benchmark-dumps-<group>-<base sha>-<CSV entry>[-<Kalshi entry>]`, so later pushes to a PR with the same base skip the whole base side. `compare` downloads each side's artifacts into one directory, compares, comments and gives the verdict.
- If the base's scripts have no `--dump` (until this check merged), nothing runs: "no baseline yet", pass.
- `scripts/compare_benchmarks.py` compares the dumps (see `tech.md`, *Benchmark comparison*). `scripts/benchmark_comment.sh` keeps one sticky PR comment (a `<!-- benchmark-report -->` marker; edited in place) with the verdict, the override state and the report; the report also goes to the run summary. Fork PRs get a read-only token, so their comment step fails softly (`continue-on-error`).
- The job fails when a guarded value is significantly worse, unless the PR has the **`benchmark-override`** label. Adding or removing a label re-runs the workflow, which reuses the verdict stored in the comment for the same head commit (seconds) instead of rerunning the benchmarks, so adding the label clears the failure. Create the label once (`gh label create benchmark-override`).
- Run time is one side's: an install, a DB build (about 1.5 minutes on a runner; none on a DB cache hit) and the three scripts at once (43 s locally; about 25 s, 5 s and 55 s one after another), plus the compare job; a cached base leaves only the head. Not a required check unless branch protection makes it one.

- **Required on `main`** (since 2026-10-08): the repository ruleset `protect` (id 24674659; it also blocks deleting `main` and force pushes) requires the `compare` check from GitHub Actions, so a PR can't merge until it passes, or until `benchmark-override` makes it pass. `compare` runs on every PR, including the ones that skip `bench`. Admins can bypass the ruleset.
- A PR whose changes are all in `docs/`, `templates/`, `site_static/`, `tests/`, root Markdown files or the other workflows can't move a benchmark: `prepare` says so, `bench` is skipped and the comment reads "Not run" (verdict skip, pass).

**Kalshi cache (`.github/workflows/kalshi-cache.yml`).** Daily at 11:40 UTC and on dispatch, main only, in its own workflow and concurrency group (until 2026-10-07 a job in `publish.yml`, where its up-to-80-minute first run kept the publish run "in progress", queued the next main publish behind it and made the hourly prices job skip): restore the newest `kalshi-markets-*` Actions cache entry, run `evaluate_markets.py --update-cache` (both market lists refetched, candlesticks for newly settled series and map 1, one request at a time; no DB), and save a new entry keyed on the cache's contents when it changed (about 10 MB compressed). The save runs even when the fetch fails or times out, so the first run (an empty cache: about 4,900 requests, ~45 minutes) keeps its progress and the next run continues; the job then fails so it shows. Kalshi's API needs no key.

## Data backup

Google Drive rate-limits the shared Oracle's Elixir CSVs ("Too many users have viewed or downloaded this file recently"; every daily run from 2 to 7 Oct got that refusal on all three attempts, with `gdown --folder`, which fails the whole folder when any one of its 13 files is refused). Since 2026-10-07 `scripts/download_data.py` lists the folder and downloads each file on its own: only the current year's (and last year's in January) when `data/raw` has the rest, or every file with `REFRESH_DATA=full`. A file replaces the old one only when it parses and has games after the old file's newest, so a refused, broken or not-yet-updated download changes nothing; a single 2026 file downloaded fine on 7 Oct while the folder download was refused. Oracle's Elixir updates them once a day, before the 10:00 UTC cron, so builds download at most once per *data day* (10:00 to 10:00 UTC): a `main` build whose cache has no `oracles-elixir-day-<day>` entry sets `REFRESH_DATA=1` (`full` on Mondays, in case an older year was corrected); every other run, and every PR, builds from the newest cached CSVs without touching Drive. A failed download falls back to the Actions cache and then, on `main`, to gzipped copies in `s3://$DATA_BACKUP_BUCKET/prometheus/oracles-elixir/`. A successful Drive download is synced back there, so the backup always holds the newest good data. PR builds can't assume the AWS role, so they rely on the cache that `main` builds save. With no data from any source, the build fails rather than publishing an empty site.

The Actions cache (about 225 MB an entry; GitHub keeps 10 GB a repo and evicts entries unused for 7 days): every build restores `oracles-elixir-day-<today>`, or else the newest `oracles-elixir-*` entry, before `setup_db.sh` (`actions/cache/restore`). Only a `main` build whose download brought newer games saves, as `oracles-elixir-day-<day>`, so there is at most one entry a day, and a failed day, or one before Oracle's Elixir updated, saves nothing (the next `main` run retries). `setup_db.sh` waits 10 s between its three attempts (30 and 60 s until 2026-10-07; the refusal lasts hours). Until 2026-10-07 every run, PRs included, re-downloaded (and until earlier that day saved a new entry keyed on the run id, which passed the 10 GB limit; the 45 left were deleted by hand on 7 Oct, taking the cache from 10.7 GB to 0.5 GB).

When the data falls behind anyway, the site says so: the home page's title line and the Predictions page show "Games through <date>" (the newest game in the DB), and `build_site.py` prints a `::warning::` annotation when the prediction log has settled matches more than 36 hours old that the data lacks (`schedule.missing_results`).

## Prediction log

`s3://$DATA_BACKUP_BUCKET/prometheus/predictions/predictions.json` holds every call saved before its match and the results (the deploy role has read-write on the whole bucket; the bucket is versioned, so an overwritten log can be restored from S3 versions). Main builds restore it before `build_site.py` and copy it back after, so calls accumulate across days. Both workflows go through `scripts/prediction_log.sh`: `restore` fails the run on any S3 error other than a missing file (until 2026-10-07 any error, a throttle or a network blip, read as "no log yet", and the build would have written a new 30-day log over the real one), and records the backup's ETag; `save` refuses a log with fewer matches than the backup (the log only grows). The publish build's save replaces the backup even if it changed since the restore (with a warning), because its log has the day's new calls; the hourly prices job saves with `--if-unchanged`, skipping the hour when the backup changed since its restore. PR builds can't reach it and start a fresh log (with a 30-day reconstructed backfill) that is thrown away. If the file is lost, the next build starts a new log and the "saved before the match" record restarts from that day. The site is rebuilt once a day (10:00 UTC), so a match's saved call uses the data through the previous day.

## Kalshi prices

`s3://$DATA_BACKUP_BUCKET/prometheus/markets/market_prices.json` holds Kalshi's last price before each past series, for the game logs on team and player pages. Main builds restore it before `build_site.py` (read-only; the build never writes it). It is refreshed by hand: run `scripts/evaluate_markets.py` (slow, fetches Kalshi), then `scripts/export_market_prices.py`, then `aws s3 cp data/market_prices.json s3://$DATA_BACKUP_BUCKET/prometheus/markets/market_prices.json`. Without it, logs show only the prices saved in the prediction log.

## Notes

- **Rolling back.** Within 7 days (the artifact's retention), re-run the `deploy` job of the earlier run (Actions → that run → Re-run jobs → `deploy`, or `gh run rerun <run id> --job <deploy job id>`): it uploads the differences between that run's site and the manifest, then invalidates. Older than that, revert the commit and let the publish rebuild (today's data, the old code), or restore objects from S3 versions (the bucket is versioned) and then delete `deploy/manifest.json` so the next deploy uploads everything. Do the same after any change to `current/` made outside `deploy_site.py`, including re-running a deploy from before 2026-10-07 (it used `releases/`).
- `releases/` is no longer written. The old releases (about 290 MB each since 2026-10-06; 7.4 GB in the bucket on 6 Oct) expire under the lifecycle rule 14 days after they were written, and their noncurrent versions 30 days after that; no manual delete is needed. S3-version rollback therefore reaches back 30 days.
- GitHub disables scheduled workflows after 60 days without repository activity. If the daily rebuild stops, re-enable it under Actions.
- The old GitHub Pages site (`thaiv28.github.io/Prometheus`) should be turned off once the AWS site is live.

## Hourly Kalshi prices (`.github/workflows/prices.yml`)

- Runs at :17 every hour and on manual dispatch; main only; about a minute. Installs with `uv sync --frozen --no-dev` (no ruff or pytest).
- **External trigger (since 2026-10-06).** GitHub's scheduler is best effort: on 6 Oct it started this hourly job once in about 12 hours, and the daily publish (10:00 UTC) starts 4–9 hours late most days. A cron-job.org job (account owned by the repo owner) POSTs `https://api.github.com/repos/thaiv28/Prometheus/actions/workflows/prices.yml/dispatches` with body `{"ref":"main"}` every hour at :17, authenticated with a fine-grained personal access token limited to this repository with only *Actions: read and write*. Dispatched runs start at once. The GitHub schedule stays as a backup; a duplicate run is harmless (concurrency group `kalshi-prices` runs them in turn). If prices stop updating, check the cron-job.org job's history (a 401/403 means the token expired or lost its permission; renew it and update the job's `Authorization: Bearer` header).
- Skips the hour while a `main` publish run is queued or running (`gh run list --branch main`; PR runs of `publish.yml` never touch the log and, until 2026-10-07, made it skip too): both read and write the prediction log, and publish holds it for several minutes between restore and save. If a publish saves between this job's restore and save anyway, `prediction_log.sh save --if-unchanged` leaves the publish's log in place.
- Steps: restore `data/predictions.json` from the backup bucket (`prediction_log.sh restore`), `scripts/update_prices.py`, save the log back (`prediction_log.sh save --if-unchanged`), copy `kalshi.json` and `predictions.json` into the site bucket's `current/` with `Cache-Control: max-age=300`, then post the alert.
- No CloudFront invalidation (since 2026-10-07): two paths an hour is about 1,440 a month, over the free 1,000. The distribution uses the managed `CachingOptimized` policy (`static-project-stack.ts` in the infrastructure repo: min TTL 1 s, default 1 day, max 1 year), which honours the object's `max-age=300`, so the edge serves the new files within 5 minutes. The publish deploy re-uploads both with the same header on every run, because a plain upload carries no `Cache-Control` and would get the 1-day default. `predictions.js` fetches `kalshi.json` with `cache: "no-store"`, which skips the browser cache but not CloudFront's, so a page sees prices at most about 5 minutes behind the job; `predictions.json` is only a link and may sit in a browser's cache for 5 minutes.
- Uses the same role as the publish workflow (`AWS_ROLE_ARN`: backup bucket read-write, site bucket write) and the `DATA_BACKUP_BUCKET` and `DEPLOYMENT_BUCKET` variables.
